## 结论
OpenRevelare 的价值主张清楚：在本地完成整卷负片反转，把可复用的底片校准与逐帧成片调整分开，并保存可重算的工程。Core 与 UI 分离、金标准回归、原子导出和跨平台构建，是值得保留的工程基础。

从产品负责人的角度，我会支持继续打磨核心工作流，但暂不支持把“可放心归档和重开”作为已经充分兑现的质量承诺。首要投资应放在保存、校正状态恢复、删除撤销和批量任务恢复。功能清单已经较长，继续增加输出格式或高级参数的优先级低于修复这些信任问题。

这是一份代码及界面材料审查，并非真实用户研究。没有用户转化、留存、支持成本或对照实验数据，不能据此推断市场规模、商业成功或用户满意度。

## 1. P1：关闭窗口时，保存失败不能阻止退出【✅ 已修复 · 自动测试通过】

**类型：代码缺陷。**

`MainWindow.OnClosing()` 调用返回 `void` 的 `FlushRollNow()`，随后继续关闭。`FlushRollNow()` 捕获工程保存异常后直接吞掉，最后调用 `_autoSave.Discard()`。如果工程目录不可写、磁盘已满或目标文件无法替换，用户关闭后会丢失尚未落盘的调整。

还有一个相关时序风险：`AutoSaveAsync()` 在等待后台写入前就将 `_rollDirty` 设为 false；窗口关闭的同步路径只判断这个字段，没有等待 `_autoSave` 的在途任务。关闭与后台保存重叠时，关闭逻辑无法证明写入已经完成。这一分支需要用受控延迟写入测试进一步验证。

**证据：** `src/OpenRevelare.Gui/Views/MainWindow.axaml.cs:1202`；`src/OpenRevelare.Gui/ViewModels/MainViewModel.cs:4583`、`:4778`；`src/OpenRevelare.Gui/Services/RollAutoSave.cs:61`。

**建议：** 统一关闭与切卷的保存协调逻辑。关闭事件先暂停退出，等待当前写入和最新修订保存；失败时保留窗口和编辑状态，提供重试、另存恢复副本、明确放弃修改三个动作。封面保存失败可以降级，工程保存失败必须明确处理。

**验收：** 保存目录只读、磁盘不足、保存中立即关闭、保存中继续编辑后关闭四种场景，都不能静默丢失最后一次调整。

## 2. P1：已关闭的 LCC 校正会在重开后重新启用【✅ 已修复 · 自动测试通过】

**类型：代码缺陷。**

工程序列化写入每帧的 `lcc_enabled`，但反序列化没有读取这个开关。加载工程只要能载入 LCC 参考，就给每帧重新赋值 `LccFlatField = lcc`，并设置 `LccEnabled = lcc is not null`。

因此，“载入参考 → 关闭 LCC → 保存 → 重开”不能恢复用户关闭校正的选择。影响不只是开关外观，而是处理像素和标定依据。

**证据：** `src/OpenRevelare.Core/Project.cs:401`、`:506`；`src/OpenRevelare.Gui/ViewModels/MainViewModel.Project.cs:450`、`:458`。

**建议：** 将“参考可用”和“用户启用”作为两个独立持久化状态。明确卷级或帧级的模型语义；旧工程缺少字段时采用有文档说明的兼容默认值。

**验收：** LCC 开启与关闭两种工程保存/重开后，开关和输出像素分别一致；缺失参考时仍保留原启用意图，以便恢复参考后正确重算。

## 3. P1：校正参考缺失可能静默降级，并在后续保存中改变工程语义【✅ 已修复 · 自动测试通过】

**类型：代码缺陷。**

打开工程时，LCC 路径不存在会绕过载入分支；Path A 的 RGB 路径和参考目录均不存在时，也可能直接跳过计算。两处只有抛出异常才设置 warning，因此“文件缺失”未必进入最终的明确告警。UI 虽会显示未载入平场等状态，但没有保证给用户一个“该工程原有校正现在缺失”的持续提示。

随后，帧会采用空校正矩阵或空平场运行。`BuildProjectData()` 又用 `_decoupleMatrix is not null` 推导 Path A/B；原 Path A 工程若因参考丢失而无矩阵，用户后续编辑触发保存，就可能将它写成 Path B。这把暂时的资源故障转成了工程语义变化。

**证据：** `src/OpenRevelare.Gui/ViewModels/MainViewModel.Project.cs:313`、`:330`、`:385`、`:475`；`src/OpenRevelare.Gui/ViewModels/MainViewModel.cs:4553`。

**建议：** 单独保存声明的处理路径和运行时资源状态。加载前检查原片、RGB 参考、平场与自定义 LUT 依赖；缺失时明确列出，提供重新定位。允许查看降级预览，但用持续横幅提示；导出前明确处理缺失项，不能默默改写原工程意图。

**验收：** 移动或删除参考后重开，再编辑保存，工程仍保留 Path A 和参考声明；恢复参考后能回到原来的处理路径。LCC 缺失必须产生可发现、可操作的提示。

## 4. P1：移除帧会删除副本并清空撤销历史【✅ 已修复 · 自动测试通过】

**类型：代码缺陷与交互风险。**

移除入口直接调用 `RemoveFrames()`。删除真实帧会同时移除其全部虚拟副本；之后 `ResetUndoAfterStructural()` 清空 `_undo` 与 `_redo`。用户既不能撤销这次移除，也会失去之前的调整撤销历史。自动保存会进一步持久化这个结果。

源照片不会因此删除，但逐帧裁切、调整和副本差异仍是用户资产。重新导入照片不能还原这些编辑。

**证据：** `src/OpenRevelare.Gui/Views/MainWindow.axaml.cs:2501`；`src/OpenRevelare.Gui/ViewModels/MainViewModel.Roll.cs:23`、`:1321`。

**建议：** 引入稳定帧 ID 和可撤销的结构操作，将删除帧及其副本作为一个事务保存。短期至少明确提示影响数量、提供恢复入口，并在不可撤销动作前保存恢复快照；增加确认框只能作为临时保护。

**验收：** 对带多个精调副本的真实帧执行移除，撤销后帧顺序、参数、副本和选择状态全部恢复；用户之前的调整历史仍可用。

## 5. P2：批量导出遇到单帧错误后缺少结果清单和续跑能力【✅ 已修复 · 跨重启回归通过】

**类型：已确认的功能缺口。**

`ExportRollAsync()` 使用包围整个循环的异常处理。任一帧解码或写入失败会结束整批，只把异常写到状态栏。此前输出保留，但没有完成/失败/未执行清单，也没有失败项重试。取消虽然提示保留已完成文件，同样没有数量与任务清单。

已有文件重名策略可以减少覆盖，却不能等价替代任务恢复：“另存新名”重跑会重复输出；“跳过”无法证明已有文件来自同样参数的本次任务。

**证据：** `src/OpenRevelare.Gui/ViewModels/MainViewModel.Roll.cs:1643`–`1704`。

**建议：** 每帧保留执行状态、源路径、输出路径、参数修订及错误原因。损坏单帧可按用户选择继续；磁盘不足等系统性错误暂停任务。完成后展示结果清单，支持重试失败/未执行项与打开目录。

**验收：** 36 帧中第 18 帧故障，用户能准确看到已完成数量、失败文件和未执行数量；重试只处理需要处理的项目，不重复生成前 17 帧。

## 6. P2：原片重定位只验证文件名【✅ 已修复 · 自动测试通过】

**类型：代码层面的完整性风险。**

`Project.Relink()` 在用户选择的目录中找到同名文件就替换路径，没有核对尺寸、设备信息或内容指纹。相机跨卷重复文件编号时，选择错误目录可能把旧调整绑定到另一张照片，并将路径自动保存。

**证据：** `src/OpenRevelare.Core/Project.cs:212`；`src/OpenRevelare.Gui/ViewModels/MainViewModel.cs:4821`。

**建议：** 保存轻量源指纹及尺寸，重定位时给出匹配置信度；不一致项先预览并确认。整文件哈希可按需计算，避免每次加载大扫描件都完整读盘。

**验收：** 两个目录含同名但不同内容的原片，错误目录不能被无提示地认定为成功修复。

## 7. P2：自动保存承诺缺少持续可见的状态【✅ 已修复 · 自动测试通过】

**类型：体验建议，基于当前绑定实现。**

工程保存是核心产品承诺，但 `RollAutoSave.IsDirty` 没有形成面向用户的独立状态；主要状态栏使用 `DisplayStatus`，会被长任务或后续操作状态替换。指南要求用户“等自动保存完成”，界面却缺少清晰、持续的完成依据。

**证据：** `src/OpenRevelare.Gui/Services/RollAutoSave.cs:34`；`src/OpenRevelare.Gui/ViewModels/MainViewModel.Tasks.cs:24`；`src/OpenRevelare.Gui/Views/MainWindow.axaml:267`；`src/OpenRevelare.Gui/Assets/docs/FIRST-ROLL.md` 第 5 节。

**建议：** 独立显示“待保存 / 保存中 / 已保存 / 保存失败”，提供工程路径和最后成功时间。失败状态持续到恢复，不被普通预览消息覆盖。任务进度和保存状态分开呈现。

**验收：** 用户不读文档即可判断现在关闭是否安全，保存失败时可以直接进入重试或恢复副本流程。

## 8. P2：输出空间是渲染参数，但处于容易被理解为导出设置的位置【✅ 交互已改进 · 用户验收待做】

**类型：产品权衡，非判定为算法错误。**

底栏输出空间控制整卷渲染语义，切换时保留调整数值并让画面变化；导出对话框只报告这个空间。代码和 tooltip 已说明行为，但用户为了分享临时改成 sRGB 时，可能没有意识到自己在改变已编辑的整卷。

**证据：** `src/OpenRevelare.Gui/ViewModels/MainViewModel.Roll.cs:87`；`src/OpenRevelare.Gui/Views/MainWindow.axaml:827`；`src/OpenRevelare.Gui/Views/ExportDialog.axaml` 的 `SpaceRow`。

**建议：** 当前架构下先明确命名为“整卷渲染空间”，并在切换前说明影响范围、提供对比和恢复。分享/后期/归档输出预设可以减少决策，但应明确是导出转换还是创建另一份渲染，避免暗中重解释既有调整。

**验收：** 用户能完成“一卷同时交付分享 JPEG 和后期 TIFF”，并清楚知道是否改变了工程、是否产生另一种观感。

## 产品 VP 的判断

### 聚焦的核心用户

建议把“有稳定翻拍或扫描流程、需要批量处理并长期保留工程的胶片摄影者”作为当前主目标用户。这是由现有产品能力推导出的定位建议，需要访谈验证。科研与商业级绝对色彩还原没有被当前工程依赖恢复和真实设备验收充分支撑，不适合扩大承诺。

### 下一阶段的资源分配

1. 首先修复四项 P1，形成“编辑 → 关闭 → 重开 → 重算”完整验收链。
2. 其次补齐批量任务报告、保存状态与资源重定位，减少用户返工和支持成本。
3. 再优化首次成功导出的时间，以及高级功能的渐进披露。
4. 最后依据真实使用和支持问题决定是否扩充高级功能。

### 衡量成功

建议的核心指标是“成功完成整卷交付并可恢复工程的用户比例”，并同时记录首张可用导出时间、保存失败率、重开一致率、批量导出完成率、失败后恢复时间。当前没有这些实测数据，不给产品打看似精确的总分。

本地优先产品可以先用本地诊断与自愿提交的测试结果建立基线；不需要为了度量引入账户或默认上传原片。

## 产品经理的体验判断

### 已经做对的部分

- 当前界面用“01 底片校准 / 02 成片调整”表达阶段，比仅暴露技术术语清楚。
- 首次启动已有离线操作指引，“第一卷”文档也定义了各阶段完成标志和失败恢复方式。
- 导入默认整卷分析，并明确提示临时预览会在分析后变化。
- 同步已有明确的分组与批量事务；导出已有命名实例和重名策略。
- 颜色诊断、输入解释和技术报告为专业用户提供了可追溯依据。

### 仍应改善的流程

- **首次使用：** 当前首次启动打开文档，导入同时提供光源路径、扫描分割、平场和自动分析。建议默认主路径以添加照片和导入为中心，参考校正按需要展开；文档指引转成可恢复的任务进度。已有默认值无需重复增加另一套向导参数模型。
- **校准：** 明确区分“当前帧调整”和“卷级应用”，在批量动作前展示来源帧、目标数量和分组摘要。不要只依赖勾选框与当前高亮的细微区别。
- **导出：** 先让用户选择分享、后期或归档用途，再展示可修改的格式、色彩标记、尺寸和兼容性结论。高级 HDR/线性输出保持可达，但不成为首次导出的必答题。
- **归档：** 提供依赖清单和相对路径优先的归档方式。工程副本只保存参数，用户需要明确知道还必须带走哪些参考与 LUT。
- **异常：** 从单条状态栏升级为可恢复的错误记录。对保存、参考缺失和部分导出失败分别给出下一步动作。

这些属于设计假设，应通过 5–8 位目标用户的任务测试验证：不看说明导入一卷、调整一帧、同步选定帧、导出分享图、移动工程后重开。记录完成率、误操作和求助点，不用主观“高级感”替代验收。

## 工程负责人的判断

### 保留的基础

Core 与 Avalonia 分离、处理管线版本明确、像素级金标准、色彩管理契约、批量编辑事务、原子导出，以及三平台 CI，是可持续发展的基础。1,034 项测试通过是积极证据，但无法代替故障场景和实际显示设备验收。

### 应按职责收敛的复杂性

`MainViewModel.cs` 有 4,867 行，`MainViewModel.Roll.cs` 有 1,952 行，`MainViewModel.Project.cs` 有 1,058 行。partial 文件改善了阅读组织，但保存、加载、渲染、批量任务和结构编辑仍共享大量可变状态。

建议以此次缺陷为边界逐步抽出工程保存协调器、工程依赖解析器、可撤销的卷编辑事务和批量导出任务模型；先明确修订号、快照和任务所有权，再移动代码。单纯按行数拆文件不会解决状态竞争。

`AtomicFile.WriteAllText()` 使用固定的 `path + ".tmp"`，同工程多写入者没有明确协调。关闭保存与自动保存重叠、多窗口或多进程打开同一工程时，这值得专门验证。可采用独立临时文件名与单写入协调/工程锁；原子替换保证文件完整，并不自动保证最新修订获胜。

### 最有价值的新增验证

优先补充四类工作流回归：关闭保存失败与在途写入；LCC 开关 round-trip；Path A/LCC 依赖缺失后保存；移除与虚拟副本撤销。随后增加批量任务部分失败恢复与重定位误匹配用例。

现有性能基线来自合成 TIFF，记录也明确排除了真实 RAW、Avalonia 位图与合成器。因此其数据只能作为组件性能证据，不能宣传成完整桌面交互延迟。应补实际大 RAW、整卷、缩放拖动和低内存设备的端到端基线，再决定优化投入。

## 建议验收顺序

1. 编辑可靠落盘，失败时保留工作；关闭与保存有唯一协调入口。
2. 参考、开关和处理路径能够完整恢复，不静默改写语义。
3. 用户删除或批量修改后能够恢复；副本与逐帧参数一起恢复。
4. 批量导出部分失败可定位、可重试，已有成功输出不重复生成。
5. 目标用户能不依赖长文档完成首卷交付，并理解工程归档所需资源。
