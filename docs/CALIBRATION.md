# chroma_grade 的来源与现状

本文记录 `chroma_grade = 3.05` 这个默认值的实际出处、它与文档曾经的说法之间的差距，以及为什么下一步是做真正的色彩空间渲染。写下来的目的是：这个值曾经被多份文档以"实测标定"的确定语气描述，而追溯下来它的依据比那种语气所暗示的弱得多。

## 出处

追溯到 Python 原型仓库 NegativeConvert 的两个提交：

- `0cc7704`（2026-05-30）引入密度域亮度/色度分离，`chroma_grade` 首次出现，默认 2.75。
- `5f5d317`（同日）改为 3.05，commit message 写 "precise Gold 200 cc24 calibration"。

当时 README 记录的标定方式：

> - 数据来源：DiVERE 对 Kodak Gold 200 + ColorChecker 24 的密度测量（D55 光源，Endura Premier 相纸）
> - 标定方法：寻找使管线反转后平均饱和度（18 个彩色色块）恢复至真实场景水平（0.806）所需的 chroma_grade
> - 结果：chroma_grade ≈ 3.05（理论值 1.67 只能还原 79%，3.05 还原至约 97%）

数据文件是 DiVERE 的 `config/colorchecker/kodak_gold_200_kodak_endura_premier_d60_cc24data.json`。

## 与文档旧说法的四处出入

**其一，那不是"实测"，是光谱模拟。** 数据文件自己的描述字段写着"在 `kodak_gold_200_auc_noDIR` → `kodak_endura_premier_d60_uc` 打印流程下，相纸上得到的**理论密度**"，`"type": "DensityExp"`。整条链路的唯一实测输入是 ColorChecker 的标称 Lab 值（X-Rite `ColorChecker24_After_Nov2014.txt`），其余由胶片感光度曲线与相纸染料响应正向算出。没有相机、没有扫描仪、没有实际拍摄。

这不是说数据不可信 —— 光谱模拟避开了翻拍眩光、光源不均、传感器噪声、采样偏差，作为基准往往比自己拍一张色卡更干净。问题只在于文档把它称作"实测"。

**其二，归因与数据集自相矛盾。** `0cc7704` 把 21% 的缺口归给"dye inter-layer cross-talk and DIR couplers"，但所用文件名是 `auc_noDIR` —— DIR 效应在这份数据里被显式关闭。DiVERE 另备有 `portra_160_DIR` / `portra_400_DIR` 版本，说明 DIR 在其建模中是可选开关。因此这 21% 不可能来自 DIR。

**其三，标定域与输出域不一致。** 数据的 `required_working_colorspace` 是 `KodakEnduraPremier`，那个 0.79 是**相纸色域下**的饱和度。而管线输出 sRGB，中间并不存在相纸这一环。

**其四，它不含任何相机信息。** DiVERE 里补偿传感器串扰的是逐卷拍色卡求解的 CCM 矩阵（`divere/utils/ccm_optimizer/`），与这份 cc24 理论数据是彼此独立的部件。因此 THEORY.md 曾称 3.05 是"相机 sensor 特性的标定结果"、并据此让 RAW 用 3.05、扫描件用 1.0 —— 这个依据不成立。同一张底片用相机翻拍和用扫描仪扫会得到两种色度渲染，而这个差异没有物理依据。

## 两项测量

**`calibration/study_saturation.py`** —— 原型时期唯一的量化脚本，曾只存在于一个 delete commit 里，现已恢复。它在合成负片上正向建模 C-41、走真实反转管线、再测饱和度还原率。结论与 3.05 相反：

```
true scene saturation              : 0.8399
MODEL 1  纯逐通道 γ（无串扰）
  restoration ratio                : 113.9%
  → scalar comp needed             : 0.000
MODEL 2  γ + 代表性染料串扰
  restoration ratio                : 111.1%
  → scalar comp to hit scene sat   : 0.000
```

反转后饱和度不降反升 11–14%，所需补偿为 0。该脚本另测出：标量补偿后每色块饱和度误差 mean 0.093 / max 0.206 —— **标量补不平**。

需要说明的是，这是合成负片 + 当前管线，不是当年的原始数字，中间管线改过（线性域解耦等）。它不足以判定"3.05 从来就是错的"，但它是仓库里唯一可执行的证据，方向与 3.05 相反。

**`calibration/gamut_check.py`** —— 检验"21% 主要来自相纸窄色域"这个假设。结果是 sRGB/Endura 饱和度比 **1.062**，色域只解释约 6%。**该假设不成立**，缺口的主要来源至今未确认。

## 结论与去向

综合来看：3.05 是从一份相纸色域的光谱模拟数据里，用一个已被测出补不平的标量拟合出的经验值，其归因与所用数据集矛盾，且不含任何相机信息。**它缺乏文档曾赋予它的那种正当性。**

真正的问题是：反转输出的线性数据从来没有声明过自己的色彩空间 —— 隐含地"反正是 sRGB"。没有色域可以转换，一个作用在色度向量上的标量就成了"颜色不对"时唯一能拧的旋钮，而色域关系本质上是各向异性、逐色相的，标量无法表达。

因此方向是做真正的色彩空间渲染：工作空间（默认 ACEScg，色域足够大，中间步骤不裁信息）+ 可选输出空间（sRGB / AdobeRGB / DisplayP3 / Endura Premier / Kodak 2383）+ gamut mapping。渲染到相纸色域会以正确的方式给出相纸观感，`chroma_grade` 随之失去存在理由。

## 色彩空间渲染的现状

已落地的部分：

- **`ColorSpaces.cs`** —— 六个空间的原色定义（sRGB / AdobeRGB / DisplayP3 / ACEScg / Endura Premier / Kodak 2383，取自 DiVERE）与 Bradford 白点适配。矩阵对照公开参考值验证：三个标准空间的 RGB→XYZ 吻合到 6 位小数，往返为单位阵，跨 D65/D60 白点适配后白仍映到白。
- **`OutputRender.cs`** —— 色域变换 + gamut mapping（`Desaturate` 保色相保亮度，`Clip` 逐通道截断）+ 各空间的编码曲线。`FromSrgbEncoded` 处理管线已经烘进 sRGB TRC 的情况：逆变换回线性、变换、再按目标空间编码；sRGB 目标是逐位不变的 no-op。
- **`IccProfiles.Build(ColorSpaceDef)`** —— 为任意注册空间生成 ICC，D50 适配后的原色由色度坐标推导。sRGB / AdobeRGB 仍走原有硬编码路径，产物逐字节不变。
- **导出对话框**与 CLI `--color-space` 提供选择，嵌入的 Profile 与实际写入的像素一致。

验证覆盖：色域变换的往返、中性轴保持中性、in-gamut 像素不被 mapper 触碰、窄化方向上 desaturate 的亮度误差为 0 而 clip 会抬高亮度、ICC gamma 标签与 `Encode()` 实际施加的曲线一致、以及 TIFF/JPEG 落盘后 Profile 确实嵌入且正确。

**一个当前的实情**：gamut mapping 选项目前是**惰性的**，已在界面上禁用并注明。原因是所有可选目标空间都比 sRGB 宽，而反转结果目前就落在 sRGB 里，不存在超出色域的颜色。它要到工作空间换成 ACEScg 之后才开始起作用 —— 那正是下一步。

## 输入端表征：chroma_grade 真正的替代品

原本的计划是把工作空间换成 ACEScg。动手后发现这个方向站不住：

- **Stage 2 是 display-referred 的**：对比度以 0.5 为轴、gamma 与曲线钳制在 [0,1]、luma 权重就是 sRGB 的 0.2126/0.7152/0.0722。把 ACEScg 的值喂进去，每个滑块的含义都会静默改变，既有工程的 Stage 2 设置会渲染出不同结果。
- **更要紧的是,反转输出的本来就不是 sRGB**。它是相机/扫描仪的原生数据跑完密度运算的结果。管它叫 sRGB 是权宜的标签,改叫 ACEScg 同样武断 —— 数字没变,只是换了个说法。

真正的缺口是**输入端从未被表征**。这才是 chroma_grade 生根的地方:输入的原色未知,就没有变换可做,标量于是成了唯一的旋钮。

因此改为从相机自身的色彩数据取矩阵（LibRaw 的 `RgbCamera`，即相机 cam_xyz 与 XYZ→sRGB 的复合），在反相之后、Stage 2 之前应用：

- **位置**：必须在反相之后。密度运算（`t_base` 归一化、`wb_high`/`wb_offset`、`d_max`）全部标定在传感器自己的数字上，提前换空间会让这些测量全部失效。也必须在 Stage 2 之前，因为 Stage 2 的定义都以 sRGB 为准。
- **中性轴不动**：矩阵行和为 1，反相确立的白点原样保留。
- **实测效果**（Olympus E-M5 III / OM-5，同一组矩阵）：色度整体展宽约 **1.32×**，且**逐色相不同**（六个探针上 1.14–1.53）。这正是 chroma_grade 用一个各向同性标量在模仿的事 —— 而各向异性是标量原理上做不到的。
- **必须做色域映射**。表征矩阵有很大的负非对角元 —— 那正是"按色相展宽色度"的含义 —— 所以它会把大量颜色推出 [0,1]：在 OM-5 矩阵上以 21³ 网格扫单位立方，**47.3% 的样本某个通道低于 0，47.4% 高于 1**。

  最初这里是逐通道钳制，那会同时移动色相与亮度，因为三个通道被挪动的量不同。实测一个饱和色的亮度从 **0.113 变成 0.248**（翻了一倍多）—— 这就是饱和画面上"颜色溢出"的来源。改用 `Desaturate`（朝自身亮度的中性轴收缩）后，六个探针的亮度误差全部为 **0**，中性轴与 in-gamut 像素不受影响。

  这个错误值得记下来：我在输出端专门论证过逐通道钳制会移色相，转头却在输入端用了它。同一件事的两侧要用同一个判断。

扫描件不参与：ICC 路径已经完成表征，再做一次就是双重变换。

### LibRaw 认不出的机身：内置后备表

打包的 LibRaw 是 **0.21.5**，相机表有 1181 台，但停在若干在售机身之前 —— OM System 系列里**只有 OM-1**，**没有 OM-5**（2022 年 10 月发布）。这类机身 LibRaw 能正常解析 ORF 容器（照片打开无碍），但 `RgbCamera` 返回**单位阵**，即"没有色度数据"，管线于是退回未表征状态。

`CameraMatrixFallback.cs` 是手工维护的补充表，键是 `"MAKE MODEL"`，值是相机公布的 DNG **ColorMatrix2**（XYZ D65 → 相机原生）。

**表是生成的，不是手打的。** `docs/calibration/gen_fallback_table.py` 读 rawspeed 的 `cameras.xml`（随 darktable 安装，`/usr/share/darktable/rawspeed/cameras.xml`）批量生成，当前 **1269 条**。rawspeed 公布的就是相机厂商的 DNG ColorMatrix，以 ×10000 的整数存放 —— 和 Adobe DNG Converter、LibRaw 用的是同一份数据。换一份更新的 `cameras.xml` 重跑脚本即可刷新。

**键必须按 LibRaw 的写法。** LibRaw 把 OM-5 的 make 报成 `OM Digital`，而文件里写的是 `OM Digital Solutions`，rawspeed 的 `<ID>` 又写 `OM System`。脚本因此为每台机身发出所有可能的拼法，多个键共享一个矩阵是正常的。字典是大小写不敏感的，所以脚本也按不敏感去重（`FUJIFILM` / `Fujifilm` 只留一条）。

另外记一笔：rawspeed 给 OM-5 和 E-M5 Mark III 的是**同一组矩阵** —— 同代 20MP 传感器，rawspeed 自己判定可以复用，不是我做的替代。

**表里的每一条都必须是实测的，不能凭记忆写。** 编一个看起来合理的矩阵比不填更糟 —— 界面会声称"已表征"，喂给管线的却是虚构。（`read_dng_matrix.py` 仍然保留：rawspeed 里没有的机身，可以用 Adobe DNG Converter 转一张再读出来。）

**全表校验**：1269 条全部产出良态变换 —— 无退化矩阵、无异常对角元、中性轴保持到 1e-6。

**推导过程有个陷阱，值得记下来。** 从 ColorMatrix2 得到 camera→sRGB，必须先把矩阵按 D65 白点做行归一化（让相机把 D65 白看成 (1,1,1)）**再求逆**，即 dcraw 的 `cam_xyz_coeff` 过程。看起来更直接的做法 —— 先算完 camera→sRGB 再把结果的行归一化到和为 1 —— 是错的：它同样能让行和为 1、也同样保持中性轴，**表面上完全正常**，但非对角元会严重偏离。在一组实测值上，绿行给出 `(-1.51, 5.31, -2.80)`，正确值是 `(-0.19, 1.79, -0.60)`。

推导与取值方式都已用 LibRaw 认识的机身反证：把 rawspeed 里 **E-M5 Mark III** 的条目喂进本模块的推导，结果与 LibRaw 自己的 `rgb_cam` 吻合到 **1.03e-4**（float32 存储精度）。同一条路取出的其余 1268 条因此可信。后备表只在 LibRaw 返回单位阵时才接管，所以 LibRaw 认识的机身仍走它自己的矩阵，两者不会打架。

实测 OM-5：色度展宽 **1.324×**，逐色相 1.144–1.529，中性轴逐位不动。

**迁移**：`roll_meta.characterise_input`，文件里没有这个字段就是 `false`。表征会明显改变颜色，因此**旧工程默认关闭**、保持原样，新建卷默认开启。用户可在「输入色彩表征」面板自行切换。

## 输入表征：三次尝试全部失败，已回退

`InputToSrgbMatrix` 这条路走不通，三种位置都在真实底片上试过并被否掉：

| 位置 | 现象 |
|---|---|
| 反相之后 | 65.6% 的颜色被压成负值，钳制即改色相，红被推向品红 |
| 反相之前 | 密度标尺崩溃，色彩大幅漂移且溢出 |
| 解码时（与扫描仪对称） | 重采样片基后仍然严重溢出、偏色 |

**根因不是位置，是矩阵与密度反相不相容。**

密度反相的运算对象是**比值** `t / t_base`，随后取 `-log10`。相机矩阵是线性变换，**不保持逐通道比值**——三个通道被按信号强度不同地混合，于是同一片密度在不同亮度处被压缩/拉伸的量不同。实测（真实 OM-5 矩阵 + 实测 t_base）：

```
t = 0.40,0.70,0.42   无矩阵 0.1444 0.1477 0.1457 | 有矩阵 0.1433 0.1484 0.1437
t = 0.15,0.30,0.20   无矩阵 0.5704 0.5157 0.4679 | 有矩阵 0.6173 0.5200 0.4270
t = 0.08,0.15,0.10   无矩阵 0.8434 0.8167 0.7689 | 有矩阵 0.8725 0.8235 0.7275
```

若两者相容，两行应当只差一个逐通道常数（那会被 `wb_high` 吸收）。实际偏差**随信号变化**且在暗部放大——蓝通道从 -0.0409 漂到 -0.0414，红通道从 -0.0011 漂到 +0.0291。这正是"溢出 + 偏色"的来源，重新采样片基不可能修好，因为错的不是基准而是变换本身。

还有一层：C-41 负片的橙色罩不是"需要被校正到 sRGB 的颜色"，而是一层滤镜，本该由 `t_base` 除掉。相机矩阵把它当作色偏来纠正（实测把 G 从 0.98 抬到 1.23），与去罩的职责直接冲突。

**扫描仪路径不受影响**，因为它的 ICC 矩阵作用在**已经过 TRC 线性化的设备 RGB** 上，而非负片的密度比值链路，两者不是同一个问题。

**结论**：相机色彩矩阵不适用于本管线。若要做真正的输入表征，正确的对象是**光谱意义上的负片响应**（逐卷色卡标定求解，DiVERE 的路子），而不是为正片场景设计的相机 ColorMatrix。`chroma_grade` 因此仍然在位——它依据薄弱（见上文），但至少不会破坏密度关系。

保留下来的成果：`ColorSpaces.cs`、`OutputRender.cs`、`IccProfiles.Build(ColorSpaceDef)`、导出色彩空间选择、软打样、`CameraMatrixFallback`（1269 台相机的矩阵表，将来若有正确用法可直接复用）。

## 治根：输入基色不该固定为 sRGB

管线从未声明解码后的负片处于什么色彩空间。没有任何一步做转换，等于隐含假定传感器的基色就是 sRGB 的基色。`chroma_grade` 是在这个假设之后、用一个下游标量去补它补不了的东西。

**DiVERE 没有 chroma_grade。** 它把**输入基色当作待解参数**，和 `gamma`/`dmax`/通道增益一起对色卡求解（`divere/utils/ccm_optimizer`）。优化器以 sRGB 基色为**起点**，但不把它当约束。因此它的矩阵与密度参数天然自洽——这正是我三次把相机矩阵硬塞进管线都失败的原因：那个矩阵是外来的，不参与求解。

`calibration/solve_input_primaries.py` 用 DiVERE 的 Gold 200 数据检验这个假设值不值得放开：

```
输入基色 固定 sRGB : MSE 1.1779   彩色块平均饱和度 0.4760
输入基色 求解      : MSE 0.8470   彩色块平均饱和度 0.5641
参考目标                          彩色块平均饱和度 0.8102
```

**放开输入基色，MSE 降 28.1%，饱和度从 0.476 升到 0.564。** 方向确认：固定 sRGB 是一个真实的、可量化的误差来源，而且它在**输入端**，不在下游。

两点必须同时记住：

- **它不是全部。** 0.564 离 0.810 仍有距离，剩余缺口来自真实的胶片效应（染料层间串扰、DIR 偶联剂），那部分不是换个输入空间能解决的。
- **单一数据集约束不足。** 解出的 G 基色 x=0.0065 撞在边界、B 落在 (0.325, 0.327)，这组基色不构成正常色域——优化器在往退化解跑。DiVERE 之所以可用，是因为它**逐卷实拍色卡**，数据来自真实拍摄链路；拿一份模拟数据集反解六个自由参数是欠定的。

**因此正确的下一步不是把这组解写进代码，而是把输入基色变成一个真实存在的、可标定的参数**（默认 sRGB = 当前行为），并提供基于实拍色卡的求解入口。没有色卡的用户保持现状，有色卡的用户可以解出属于自己那套设备与胶片的基色。

### 已落地：`InputPrimaries`

`FrameParams.InputPrimaries`（三对 CIE xy）+ `InputWhitePoint`，`InputTransform.cs` 在**反相之前、解耦之前**施加，与 DiVERE 同构。

- **默认 null = sRGB 基色 = 当前行为**。显式声明 sRGB 与 null 渲染**逐位相同**（identity 被检出并跳过整趟）。
- 施加走 Path A 的 `Decouple.ApplyLinear`，复用其 per-pixel gamut 保护 —— 基色变换和解耦矩阵一样有负非对角元，会把接近零的透射率推成负数，而下一步就是 `-log10`。
- 退化基色（三点共线）、形状错误一律拒绝并回落默认，不在渲染中抛异常。
- 工程文件读写，缺字段即默认，旧工程行为不变。

**与 `t_base` 强耦合**：片基是在这个声明的空间里采样的，改基色必须重新采样片基。两者同属卷级标定。

### 三通道对齐为什么不够

`calibration/alignment_vs_chroma.py` 量化了这件事。采片基 + 定黑白点是**有物理依据的三通道对齐**（`t_base` / `wb_offset` / `wb_high` 就是它），但它够不到色度：

```
对齐前            中性轴偏差 0.02501   彩色块饱和度 0.7237
完美逐通道对齐     中性轴偏差 0.01341   彩色块饱和度 0.7224
参考目标                                        0.8056
```

**把中性轴对齐到理论最优，饱和度纹丝不动。** 原因是结构性的：`t_base`（除）、`wb_offset`（加）、`wb_high`（乘）全是**逐通道**操作，而饱和度是**通道之间**的关系；能移动它的自由度，恰好已经被用来锚住中性轴了，两个目标争夺同一组旋钮。

约 11% 的色度差距因此**原理上**够不到，需要跨通道变换。这既解释了 `chroma_grade` 为何存在，也解释了为什么 DaVinci/PS 那条路"看起来够用"——它还原的是**中性轴**（视觉上最显眼的部分），剩下的 11% 只表现为"稍微淡一点"，不拿色卡量是察觉不到的。

一处方法学教训：参考数据文件存的是 **XYZ**（其 description 自述如此），第一次比对时我当成 RGB，得出的目标饱和度是 0.61 而非真实的 0.81，整轮结论都偏了。跨数据集比较前先确认空间。

## 通用串扰方向：从无相纸实测数据求得

### 第一次尝试失败：数据源含相纸

最初用 DiVERE 的八套 ColorChecker 数据拟合，结果必须撤回 —— 相纸在我以为的反面：

```
目标侧  original_color_cc24data.json
        "ColorChecker 24 色块原始测量值"，required_working_colorspace: None   ← 真实场景 ✓
负片侧  kodak_*_kodak_endura_premier_d60_cc24data.json
        "…打印流程下，相纸上得到的理论密度"
        required_working_colorspace: KodakEnduraPremier                      ← 含相纸 ✗
```

拟合出的矩阵映射的是 **相纸密度 → 场景**，而本管线需要 **底片密度 → 场景**，相差整条印相链路 —— 正是本软件明确不引入、只在软打样中作为模拟提供的东西。那个 0.42 的残差中相当一部分是在拟合印相链路，不是胶片串扰；此前称之为"相纸链路未建模"不准确，是**建模方向反了**。

### 可用的数据：DiVERE 的实测密度矩阵

`config/matrices/*.json` 是另一批东西：用户对**真实扫描**求解的密度校正矩阵，文件名是「扫描仪 + 胶片」，**没有相纸**。共 18 个，覆盖 Nikon 9000ED / 5000ED、Hasselblad X5；Kodak Gold 200、Portra 160/400、Ultramax 400、Fuji 100、Lucky C200，以及电影卷 5207 / 5219。

`calibration/paper_free_crosstalk.py` 先做了分离检验：

```
同胶片、不同扫描仪   5 对    mean cos +0.9944   min +0.9872
同扫描仪、不同胶片   97 对   mean cos +0.9908   min +0.9618
完全无关             42 对   mean cos +0.9848   min +0.9393
```

三组全部高度一致，同胶片仅略优于同扫描仪。**方向既不主要属于胶片，也不主要属于扫描仪。**

### 结论：这是测量方式的共性，比 C-41 更普遍

取 18 个矩阵的主方向：**单一方向解释 99.01% 的方差**，最差个体一致度 cos 0.9798。

跨扫描仪、跨厂牌染料、**跨工艺**都成立 —— 5207 同时以 C-41 和 ECN-2 冲洗出现，两者都落在这个方向上。

所以这个形状**不属于 C-41，也不属于任何染料配方**。它是「三层减色染料图像被三个宽带传感器通道读取」这件事本身的产物：染料吸收带与传感器通带必然部分重叠，通道耦合因此不可避免。**这正是"通用工艺或性质"** —— 而且比 C-41 更基础，是减色法胶片成像的共性。补偿它是物理校正，不是口味。

矩阵性质：行和与列和**均**为 0（1e-17，亮度零空间双向成立）；秩为 2；两个色度轴的奇异值 0.736 / 0.677，各向异性仅 **1.087**。对比经过相纸链路时测得的 1.5185 —— **那多出来的各向异性大部分属于相纸，不属于胶片**。

### 强度仍然不是常数

18 个矩阵的强度跨度 **0.99–1.89**，随扫描仪变，也随求解者变（同卷同扫描仪出现两次：1.41 与 1.79）。结构上

```
strength = 目标色度 / 负片色度
```

由"把什么声明为目标"决定，不是胶片属性。因此只固定方向，强度留作参数，取 18 个的中位数 1.3234 作起点 —— 是起点，不是要辩护的值。

`FrameParams.UseC41Crosstalk` 默认关闭；Path A 卷优先使用其自身解耦色度矩阵，两者绝不叠加。

## 撤回：强度预设建立在错误的测量域上

曾据 18 个实测矩阵得出"实测标定平均只做 ×0.97，不支持提升色度"，并据此做了默认中性 0 的预设。**该结论错误，已连同代码一并撤回**（`873b4d6`、`994b2e7`）。

错在测量域。DiVERE 的密度矩阵不是作用在零均值色度上，而是（`divere/core/math_ops.py::apply_density_matrix`）：

```python
input_density = density_array + dmax
adjusted = pivot + np.dot(reshaped - pivot, matrix.T)   # pivot = 4.8-0.7
result = adjusted - dmax
```

**作用于绝对密度，绕 pivot ≈ 4.1 旋转。** 而本管线的 `chroma_grade` 与我实现的矩阵分支都作用在零均值色度分量上。同一个矩阵在这两个域里效果完全不同。

在 DiVERE 的实际域中重测同样 18 个矩阵对**正片色度**的作用：

```
17/18 提升色度，均值 ×1.13，范围 ×0.82–×1.32
```

与我先前算出的"12 个降低、均值 ×0.97"方向相反。**实测标定其实是在提升色度**，这与 `chroma_grade` 的意图一致，也与用户观察一致——降低饱和度是错误方向。

**教训**：跨项目搬用矩阵前必须先确认它作用的域（绝对密度 vs 零均值色度、是否绕 pivot、是否含 dmax 偏移）。此前搬用相机 ColorMatrix 失败三次是同一类错误的不同形态。

仍然站得住的：方向矩阵本身（99.01% 方差、跨扫描仪/染料/工艺一致）以及"强度无法从中性轴自导出"的证明——两者都不依赖增益的正负。

## 完整色彩管理

`ColorPipeline.cs` 把整条链上每一段所处的色彩空间**显式声明**出来。这不是记账，而是修复本身——此前管线从不声明任何空间，解码结果直接进密度运算，输出被当作 sRGB，因为导出时就是这么写的。本文追溯的每一个颜色问题都回到这个缺口，而 `chroma_grade` 是其上的第一块补丁：没有色域可供转换时，作用在密度色度上的标量就是唯一能拧的旋钮。

### 与 Cineon 流程的对照

Cineon 没有这个参数，原因是结构性的：

```
1  解码到线性光（挂相机 profile）
2  线性 → Cineon log
3  在对数域反相、对齐三通道
4  log → Rec709：色彩空间 与 gamma 一起转
```

**第 4 步的色域变换本身就恢复了色度**，所以第 3 步不需要任何色度操作——这正是"反相 + 三通道对齐"在 DaVinci 里看起来够用的原因。本管线做了第 4 步的 gamma，**没做它的色彩空间那一半**，色度因此从未到位，只能在下游伪造。

### 链条

```
输入原色 ──InputTransform──▶ 工作空间（线性）
                                  │  −log10
                                  ▼
                          密度域：反相 / t_base / wb / grade
                          此处不应有任何色彩操作——取对数是
                          换刻度，不是换原色
                                  │  10^x
                                  ▼
                          工作空间（线性正片）
                                  │
                    ┌─────────────┴─────────────┐
              OutputRender                 OutputRender
                    ▼                            ▼
                 导出空间                     显示空间
```

**密度域没有自己的原色。** 这一点值得写明，因为它确实造成过混淆：`−log10` 逐通道换刻度，改变不了通道的含义。进入对数域时是什么原色，出来还是什么原色。

### 落地

- **`ColorPipeline.Working`** — 密度运算所在的空间，当前为 sRGB（即历史行为，声明它不改变任何输出）。加宽是最终目标，但 Stage 2 是 display-referred 的（对比度以 0.5 为轴、曲线钳制 [0,1]、luma 权重写死 sRGB），需先重构那七个操作。
- **`ColorPipeline.Render`** — 导出与预览共用的唯一出口，GUI 与 CLI 都已改走它。
- **`BitmapConvert.Display`** — 预览的显示器空间。默认 null = sRGB 直通（历史行为）；选中实际面板空间后预览才真正做色彩管理。底部工具条新增「显示器」下拉。这是视图设置：不写进工程，不影响导出——换台机器屏幕就不同了。

验证：工作空间自身往返逐位不变；线性入口与已编码入口结果一致（delta 0）；中性轴进入全部五个目标空间均保持中性；`−log10`/`10^x` 精确往返；真实底片导出 sRGB 与不转换逐位相同、导出 AdobeRGB 有实际差异且无越界。

## Stage 2 重构：区分三类假设

Stage 2 被称作"display-referred"，挡着工作空间加宽。动手前先把它的假设分了类，结果只有一类是真问题。

**第一类：写死 sRGB，必须改。** luma 权重 `0.2126/0.7152/0.0722` 是 sRGB 的 Y 行；ACEScg 是 `0.2722/0.6741/0.0537`。工作空间一旦加宽，高光/阴影、保色相曲线、饱和度四处会同时算错亮度。**已改为从 `ColorPipeline.Working` 导出**，两者不可能再走散。

**第二类：措辞像 sRGB，行为其实无关。** 对比度以 0.5 为轴、曲线的 gamma 2.2 编码 —— 这些关乎**编码**（中灰在哪、有效范围多大），不关乎原色。线性 sRGB 的 0.5 和线性 ACEScg 的 0.5 都是"半个场景白"，加宽原色不会移动中灰。**无需改动**。

曲线的 2.2 特意**保持常数而非导出** —— 它定义了用户存下的曲线控制点**是什么意思**。导出它会让工作空间一变就静默重新解释所有既存曲线，那是伪装成重构的数据兼容性破坏。

**第三类：`[0,1]` 钳制，真正的瓶颈。** 三处钳制中只有曲线那处是硬损失：编码前截断一次、解码后再截断一次。ACEScg 的红在 sRGB 坐标下是 1.23，进曲线前就被砍掉，加宽换来的余量当场消失。

**已改为让越界值穿过曲线**：曲线只在 [0,1] 上有定义，超出范围的采样保留原值、之后重新汇入。负值仍然置零（`Pow` 负底数是 NaN，且负值意味着颜色已完全出色域，由输出阶段处理）。

高光/阴影那处钳制是必要的（`Pow` 需要非负底数），且它钳的是运算数、结果按 `(1-amt)*outv` 混回，>1 的值部分存活。`BuildLut` 那处钳的是曲线自身的输出范围，与图像无关。

验证：导出的 luma 权重与原写死值逐位相同；真实底片跑满 Stage 2 无越界无 NaN；1.30 穿过曲线后仍是 1.30（此前会被压成 1.0）；负值不产生 NaN。

顺带确认一件事：对比度会让值超过 1.0（实测 1.0169），这是**既有行为**，由 sRGB 出口 TRC 收回 —— 我一度误判为本次改动引入的回归，实际是我测了不带 `srgbExit` 的路径。

## Stage 2 两段式重构：先转空间，再在该空间里调整

原先的顺序是反的：Stage 2 收到**线性**工作空间数据，却用**为显示域设计的公式**去调整，色彩空间转换发生在它**之后**。

实证两处矛盾：

```
对比度以 0.5 为轴，而线性域的 0.5 = 显示亮度的 73.5%
  => 轴心落在偏亮处，暗部被压得过狠
  实测：显示中灰经 contrast=0.5，旧链输出 0.3417，新链 0.5000

曲线内部 Pow(1/2.2) 编码 -> 采样 -> Pow(2.2) 解码，出口再套一次 sRGB TRC
  => 同一份数据编解码两轮，中间那轮只为让曲线有正确语义
```

### 按运算性质分两段

不是"全部移到转换之后"，而是按每个操作**物理上是什么**来分：

| 段 | 操作 | 理由 |
|---|---|---|
| **线性光** | 白平衡、曝光 | 缩放光量。实测线性 0.25×2 编码为 0.735，而编码域 ×2 直接截断到 1.0 |
| **↓ 编码一次** | | |
| **显示空间** | 色阶、对比度、高光/阴影、曲线、饱和度 | 感知运算，其定义只在编码域成立 |

编码只发生一次、且在中间，曲线那层私有 gamma 随之消失 —— 它存在的唯一原因就是编码来得太晚。

### 收尾钳制

旧链里出口 TRC 在最后，顺带把一切收进 [0,1]。新链的编码在前面，越界的操作后面没有兜底了 —— 对比度就是那个会越界的（实测 0.2 的设定下到 1.049，因为绕中灰旋转必然把高光抬过白点）。显示域编码值在 [0,1] 之外没有意义，因此在此显式收尾，而不是让它流到导出。

### 迁移

`FrameParams.DisplayReferredStage2`，新建卷 `true`，**工程文件里缺此字段即 `false`** —— 旧工程照旧渲染。

用版本位而不是偏好项，因为**滑块数值的含义变了**：同一个对比度数字在两条链下出的是不同的画面。既有工程没有任何部分可以被安全地重新解释。

验证：无调整时新链等同于一次纯 sRGB 编码（逐位）；对比度轴心从 0.3417 修正到 0.5000；完整链路（色阶+对比度+高光阴影+曲线+饱和度）在范围内；真实底片两条链均无越界；新工程往返为新语义、旧工程（无字段）载入为旧链。

## chroma_grade 已移除

不是改默认值，是**移除这个概念**。

Cineon 的反相是 `a = pivot + (d - pivot) * grade` —— **一个 gamma 作用于三个通道**。色度是逐通道偏差，乘同一系数时按比例保持，因此**不需要第二个参数**。把亮度与色度拆开、给色度另一个系数，本身就是对 Cineon 的偏离。

它当初被引入，是为了补管线在别处丢失的色度。而那个"别处"现在已经查明并补上了：缺的是**色彩空间转换**（Cineon 第 4 步的色域那一半），由 `InputTransform` 与 `OutputRender` 承担。**色度由色域映射补回，不再需要一个标量去伪造。**

3.05 这个值的追溯结论（相纸色域的光谱模拟、归因与数据集矛盾、标量补不平各向异性）全部保留在上文，作为它为何不该继续存在的记录。

**兼容**：工程文件仍写出 `chroma_grade`，其值等于 `grade`，以便旧版本与 Python 原版仍能读取；**载入时不再读回** —— 旧文件里存的 3.05 描述的是一次补偿，而被补偿的缺口现已由真正的色彩空间转换填上，照旧读回会重复施加。

验证：反相输出与手算的纯 Cineon 单 gamma 路径一致（偏差 2.6e-6，float32 精度）。

## Path B 不需要相机基色 —— t_base 已经承担了它

「声明相机基色」实测**关着更准**，已连同代码撤回。原因查明，而且它同时解释了为什么 Cineon 流程里也没有这一环。

### t_base 已经做了同一件事

`t_base` 是**除以片基**。它把整条链路上到片基为止的所有通道增益一次性归一 —— **其中就包括相机三通道的相对灵敏度差异**，也正是相机基色矩阵要修的东西。

实测：

```
未变换的片基   R 0.5581  G 0.9773  B 0.5824
变换后的片基   R 0.5043  G 1.2227  B 0.4143
```

片基本身会被该矩阵改变，说明矩阵正在修的偏差，`t_base` 随后又会归一一次。**先 t_base 再声明基色 = 同一个偏差被修两次。**

### Cineon 流程为何不需要

G2P（Photoshop 那条路）的 RAW 解码参数是 `dcraw -r 1 1 1 1 -o 0` —— **UniWB + raw 相机色彩空间，不挂任何 profile**，与本管线一致。它随后用 `setBlendDivide`「用片基色除全图」，其逆向笔记称之为"去罩干净的第一主线"。

**除以片基这一步，就是三通道对齐，也就是相机基色该被处理的地方。** Cineon 第 3 步「在对数域反相、对齐三通道」承担的正是这个职责，所以流程里不需要单独的相机 profile。

### 结论

Path B 的色彩链**没有缺口**。此前认为"输入基色未声明是缺陷"，判断有误：它不是未声明，而是**由 t_base 隐式承担**，且这种承担是逐卷实测的，比查表得来的相机矩阵更贴合实际拍摄条件 —— 光源、镜头、翻拍几何都被一并归一。

**这里要与 `chroma_grade` 的成因区分开 —— 两者无关。** 片基采错会偏色，但采准了也不会让 `chroma_grade` 变得必要：它补的是**色彩空间管理缺失**（反相结果被直接当作 sRGB，色域变换从未发生），而不是片基。之所以一度把两者混为一谈，是因为追查 `chroma_grade` 与发现片基采样缺陷在时间上凑到了一起，误当成了同一个因果。

「输入基色」这一项与片基有关（`t_base` 已隐式承担），`chroma_grade` 与色彩空间管理有关 —— 两条线索各自独立，各自的结论都成立。

保留 `RawDecode.CameraPrimaries`（Path A 的基色反解或许用得上），但不接入 Path B。

## 软打样

预览此前是"sRGB 编码后直接送屏"，中间没有任何色彩管理 —— `WriteableBitmap` 不带 ICC，Avalonia 也不做显示器变换。因此在广色域屏上看到的一直偏艳，这与本次改动无关，是既有事实。

现在底部工具条有「软打样」下拉：选中某个空间后，预览会走 sRGB → 该空间（含 gamut mapping）→ 回 sRGB 的往返，屏幕上呈现的就是导出到该空间会得到的样子。默认关闭，只影响预览，不影响导出文件，也不写进工程。

**只列出比 sRGB 窄的空间。** 软打样展示的是目标色域"装不下"的部分，而 Adobe RGB 与 Display P3 都比 sRGB **宽** —— 反转结果目前就落在 sRGB 里，往返它们实测最大变化 **0.000023**（不到 8-bit 的一级），即完全看不出变化。曾经把它们列进选项，结果是一个切换了却毫无反应的控件；现已移除，等工作空间加宽后再放回来。Endura（0.119）与 Kodak 2383（0.103）确有可见差异，保留。

尚未做的：工作空间本身仍是隐含的 sRGB。要让 gamut mapping 在导出时真正起作用，仍需把工作空间加宽 —— 但如上所述，那一步的前提是先重做 Stage 2 的 display-referred 假设，不是简单换个标签。
