# NegPy 路线 M0：首批组件取证与热点优化

日期：2026-11-12。实施状态：[总进度](../negpy-optimization-progress.md)。本记录只证明 OpenRevelare 的组件变化，尚未完成 NegPy 同机对照或 M0 全部验收。

## 环境与方法

- Windows 10.0.26200，.NET 8.0.29，Release；AMD Ryzen 5 5600X，6 核／12 逻辑处理器，物理内存约 48 GiB。
- NVIDIA RTX 3070，驱动 `32.0.16.1088`；配对色彩转换明确 GPU Off，本轮不是 GPU 优化。
- 修改前基线：`b16a3b2c7279a408bde3387c209ce4e76a8f0be3`。修改后为当前分支 `CanonicalPreviewConverter` 的分区版本；配对记录附程序集及 native CMM SHA-256。
- 先后运行三次独立进程的旧组件基准与三次修改后基准；随后对合成图与一张真实 RAF 各做三次独立进程配对实验。实验组未并行运行；未控制后台系统负载、CPU 频率或 OS 文件缓存。
- 下文汇总是**三次进程各自 P50／P95 的中位数**，不是合并原始样本后的分位数。现有组件基准只记录分位数；新配对基准保留全部 30 对原始耗时和分配数据。

## 原热点及改动

原有合成 TIFF 工作负载下，1200×800 规范场景转换 P50 为 131.84 ms，完整准备 151.37 ms；色彩转换是此次最大的准备成本。

大图现在分为最多四块，每块在自己的线程获取、使用并释放 LittleCMS lease，独立进行 RGB → D50 XYZ → Bradford D65 → 线性 sRGB → RGBA-half。小图、第三方 CMM 实现及原有 canonical carrier 保持原路径。CMM 精确浮点请求、ICC、两阶段矩阵算式、扩展范围与最终 half 舍入保持不变。没有改用整数预览精度，没有跳过色彩管理。

只对 bundled `LittleCmsEngine` 启用并行，因为该实现明确提供线程局部 native transform；不推断任意 `IColorManagementEngine` 都可并发。每次最多四个 worker，并不表示全进程所有调用共享四个 worker。并发导出与后台分析仍须遵守现有调度预算；native thread cache 的常驻成本需继续观察。

## 合成组件工作负载的前后对照

2400×1600 合成 TIFF，实际预览 1200×800；每次 30 次完整准备，拖动准备 12 次。完整准备包含像素管线、规范场景和直方图；拖动准备另含 CPU fallback 编码，不含实际 Avalonia bitmap 或屏幕合成。

- **规范场景转换：** P50 131.84 → 46.10 ms（减少 65.0%）；P95 142.40 → 52.09 ms。
- **完整预览准备：** P50 151.37 → 65.14 ms（减少 57.0%）；P95 177.07 → 92.17 ms。
- **800 长边拖动准备：** P50 39.65 → 18.73 ms（减少 52.8%）；P95 44.97 → 20.77 ms。
- 准备缓存查询 P50 0.340 → 0.364 ms，P95 0.674 → 0.631 ms，不能声称这条查询路径变快；未修改该缓存。
- 组件基准中的 `pipeline`、`canonical-scene` 和 `histogram` 包含一次 JIT／CMM 预热；完整准备 30 次不含预热。原始记录保留该既有口径。

原始记录：[修改前 1](negpy-m0-2026-11-12/negpy-m0-before.json)、[2](negpy-m0-2026-11-12/negpy-m0-before-2.json)、[3](negpy-m0-2026-11-12/negpy-m0-before-3.json)；[修改后 1](negpy-m0-2026-11-12/negpy-m0-after.json)、[2](negpy-m0-2026-11-12/negpy-m0-after-2.json)、[3](negpy-m0-2026-11-12/negpy-m0-after-3.json)。

## 同进程、同像素的配对复核

每次将同一份渲染像素交给串行与并行转换，预热后交替先后顺序，测量 30 对；逐对检查 RGBA-half 原始字节相同。串行对照是同一 native CMM 的接口包装，不引入不同精度或图像算法。

- **1200×800 合成图：** P50 146.11 → 49.09 ms（减少约 66.4%），P95 153.77 → 56.20 ms。
- **真实 RAF：** 输入 11648×8735（约 101.74 MP），预览 1456×1092；P50 217.95 → 76.55 ms（减少约 64.9%），P95 231.21 → 85.16 ms。
- 三次真实 RAW 的预览解码各约 3.4 s，仅各测一次，且提前哈希预热文件；不作为解码优化或冷磁盘结论。
- 真实原片大小 112,898,592 字节，内容 SHA-256 为 `8136050b3428309fcc489bf4ad2e4535af5a54f037a48a911094783f60f817a0`。三次运行前后哈希一致，未写入原片或创建工程。
- 合成配对每次托管分配约 19.20 MB；并行仅多出少量调度／lease 开销。跨线程分配全部计入，不能用只看调用线程的方法虚报节省。未据本实验宣称内存优化。

原始配对记录：[合成 1](negpy-m0-2026-11-12/negpy-canonical-generated-1.json)、[2](negpy-m0-2026-11-12/negpy-canonical-generated-2.json)、[3](negpy-m0-2026-11-12/negpy-canonical-generated-3.json)；[RAF 1](negpy-m0-2026-11-12/negpy-canonical-raf-1.json)、[2](negpy-m0-2026-11-12/negpy-canonical-raf-2.json)、[3](negpy-m0-2026-11-12/negpy-canonical-raf-3.json)。

配对实验的合成图内容与旧组件基准不同，不能把两组绝对耗时拼接为一组前后对照。峰值工作集包含解码、正确性检查和两条路径，不用于比较单条转换路径的占用。

## 正确性与构建

新增测试以小批串行结果对照大图转换，覆盖阈值两侧、非整除分区，以及 sRGB、Display P3、Adobe RGB、线性 ACEScg 的负值与大于一的值。另验证同一引擎多个转换同时进行时的像素一致性、原图不修改和 lease 释放。

`dotnet test OpenRevelare.sln -c Release --no-restore -warnaserror`：主测试 1,534 通过、10 项硬件跳过；Win32 40 通过、macOS 契约 25 通过；合计 **1,599 通过，0 失败**。平台契约测试不等于 macOS 真机测试。新增配对基准编译运行成功。

## 固定版 NegPy 同机组件旁证

使用原定提交 `d8123a9b2a18fdaab5941347a91e402fa936d3dc`（0.68.0），官方提交源码包 SHA-256 为 `9573e25f650877daedc6287ec40701e018c94cc7d8433fcf9de024066e3c1da1`。运行前后核对 581 个包／原生源码文件的 Git blob 身份，未修改上游源码。

隔离运行目录为 `artifacts/negpy-reference`，没有把第三方代码或依赖加入产品。Python 3.13.18，按 `uv.lock` 使用 NumPy 2.4.4、rawpy 0.27.0（LibRaw 0.22.1）、wgpu 0.31.1、PyQt6 6.11.0；从固定源码构建原生 `negpy_core`。GPU 实际选择 NVIDIA RTX 3070，Vulkan，驱动描述 610.88。

按上游 `tests/metrics/test_render_frame.py` 的同步边界测量：每个进程先 CPU 后 GPU，各做 30 次拖动密度变化和 30 次释放状态。拖动不回读诊断，释放回读诊断；每阶段先预热一次。GPU 分三段记录：

1. `run_pipeline` 返回的提交耗时。
2. 通过 staging buffer 映射确认此前 GPU 工作完成后的累计耗时。
3. 再回读完整 float32 RGB 图像后的累计耗时。

GPU 请求若实际回退 CPU 则失败，不计作 GPU 成绩；每次确认完整 RGB 存在且有限，并检查输入像素未改。合成图和同一授权 RAF 各执行三个独立进程，未与其他测试或基准同时运行。下表为各进程 P50 的中位数，单位 ms，不是合并样本分位数。

| 输入／状态 | CPU 成图 | GPU 提交 | GPU 完成 | GPU 完成并回读 RGB |
|---|---:|---:|---:|---:|
| 1200×800 合成，拖动 | 53.04 | 1.27 | 2.70 | 8.24 |
| 1200×800 合成，释放 | 53.69 | 5.60 | 5.83 | 11.42 |
| 1600×1199 RAF 预览，拖动 | 110.02 | 9.37 | 12.16 | 23.19 |
| 1600×1199 RAF 预览，释放 | 106.85 | 16.63 | 16.93 | 27.93 |

RAF 拖动的 GPU 完成 P95 中位为 13.30 ms，含完整 RGB 回读为 24.49 ms。GPU 提交时间不能代表图像完成，更不能当作屏幕显示延迟。

三次首次进程加载 RAF 分别为 1305.91／1151.08／1155.11 ms；缓存加载分别为 1.16／1.24／1.16 ms。这是三次单点加载观察，不是可靠分位数；运行前完整原片哈希已经预热 OS 文件缓存。原片完整 SHA-256 与上文一致，六次渲染路径均保持解码源像素不变；三次 RAF 解码像素哈希相同。

### 可以支持的取舍

NegPy 的常驻 GPU 与按需回读对其交互路径有明显价值，值得保留为后续技术依据。当前先保留已验证的 CPU／缓存实现，不为这些数字新增 GPU 后端、印相模型或界面模块。

双方实际边界仍不等价：NegPy 报告 RAF 源尺寸 11662×8746、预览 1600×1199；本软件该路径为 11648×8735、1456×1092。解码策略、有效区域、原生相机通道／工作原色、归一化与印相模型不同；上文本软件 FilmBase 实验另有暗角、拉直、裁切和齿孔负载。NegPy 的 GPU 数字不含本软件的 canonical CMM 合同，也不含 Qt 视图／屏幕发布。**不能据此给出整体软件快几倍、同画质或同色彩精度结论。**

[完整原始数据与复现脚本](negpy-m0-2026-11-12/negpy-reference-components.json) 合并保存六次结果、默认参数、环境身份及本次实际执行的脚本，避免增加多份工具或产品依赖。复现时将 JSON 的 `measurement_script` 原样写到参考目录的 `measure_negpy.py`，按固定源码和锁文件准备隔离 Python／原生核心，执行 `python measure_negpy.py results/generated-1.json` 或增加 `--input '<授权 RAF 路径>'`。没有复制用户照片；原始日志留在工作区 `artifacts/negpy-reference`。

## Windows 硬件验证补充

发现此前 10 项硬件门是显式 opt-in，不代表本机没有设备。设置 `OPENREVELARE_REQUIRE_GPU=1`、`OPENREVELARE_REQUIRE_HEVC=1` 后，先单独验证 GPU 12 项和 Main10 1 项，再运行完整解：

```powershell
$env:OPENREVELARE_REQUIRE_GPU = '1'
$env:OPENREVELARE_REQUIRE_HEVC = '1'
dotnet test OpenRevelare.sln -c Release -warnaserror --no-restore
```

结果为 **1,656 通过、0 跳过、0 失败**（主测试 1,591、Win32 40、macOS 契约 25）。覆盖实际 GPU 的重采样／锐化／LUT、完整 ManagedV2 与 canonical 结果、资源失败回退；Main10 用例重复导出 SDR／HDR、核对位深、ICC／nclx、奇数尺寸和元数据。日志为 `artifacts/negpy-reference/openrevelare-all-hardware-tests.log`。

这补上 Windows 组件层硬件证据。macOS 项仍只是契约测试；屏幕 HDR、原生窗口、多 DPI、低内存整卷和用户任务仍未验收。
