# 预览、切帧与导出的性能诊断

2026-10-17，Printroom 学习迁移第 4、5 项。自动裁剪不在本次工作范围。

## 已实现的机制

原片版本由规范化绝对路径、长度、UTC 修改时间、创建时间及 RAW 解码配置组成。缓存键另包含精确裁切区域、管线版本和 TIFF 输入解释。解码前后及发布前复核版本；换卷代数阻止旧任务恢复缓存。常驻小图、全尺寸单槽、放大区域、负片白平衡元数据与整卷分析使用相同版本依据。

平场和 Path A 矩阵记录加载时的参考快照。参考改变后要求显式重新载入／重新标定或打开工程，避免静默改变已存标定依据。该检测采用文件元数据，**不识别内容变化但所有已检查元数据均被保留的替换**；未引入全文件哈希或常驻文件监控。

邻帧预热在正式预览发布后空闲 350 ms 才开始，最多前后一帧，只使用现有解码缓存，不为推测操作启动 RAW 解码。缓存保留处理后的像素、规范场景与直方图，不保留第二份 native bitmap。容量上限为两项／96 MiB；可用内存低于 1 GiB 时拒绝读写并清空。换卷、切帧、调参、拖动和长任务取消后台工作；提交时重查帧、原片、区域、参数、LUT 和管线。

准备任务与正式异步预览共用一条渲染通道，后台只在通道空闲时进入。已经执行中的 CPU／CMM 阶段只能在阶段边界取消，不能保证瞬间抢占；实时拖动仍沿用现有的同步低分辨率路径。原片不会因为预热失败显示前台错误。

## 组件基准：可复算的初步依据

仓库根目录执行：

```powershell
dotnet run --project benchmarks/OpenRevelare.PreviewBenchmark -c Release -- scratch/performance/printroom-preview-baseline.json
```

该程序生成独立的 2400×1600 TIFF，实际预览为 1200×800（现有整数 box 缩放），使用 ManagedV2。配置与数据重定向到临时目录，所有输入和输出都是生成物。默认 JSON 写入被 git 忽略的 `scratch`；也可传入其他结果路径。

2026-10-16 的一次 Windows / .NET 8.0.29 / 12 逻辑核运行，保存于 [原始 JSON](printroom-preview-baseline-2026-10-16.json)：

- 30 次完整 CPU 准备（管线、规范场景、直方图）：P50 **153.888 ms**，P95 **186.866 ms**。
- 30 次已准备缓存查询（含文件版本及完整参数键）：P50 **0.286 ms**，P95 **0.611 ms**。
- 规范场景转换单独 P50 **135.730 ms**，比管线本身的 **16.619 ms** 更重，支持预先准备显示数据而非重写 GPU 管线的选择。
- 一项准备结果占 **19,204,096 字节**；整个基准进程峰值工作集 **475,979,776 字节**，包含生成输入、解码、放大与导出，不能当作应用预热的增量内存。
- 重新计算与缓存结果的处理像素及规范场景逐值一致。基准还记录首次读取、重复解码、800 像素拖动管线、区域渲染和全尺寸 TIFF 输出。

这是**组件基准**，不包含 Avalonia fallback bitmap、窗口合成、显示器转换或真实 RAW；OS 磁盘缓存状态未控制。不能把约 154 ms 的准备成本节省称为完整界面切帧延迟，也不能外推为所有机器的速度。

## 实际应用的可重复测量

启动前开启既有日志开关：

```powershell
$env:OPENREVELARE_RENDER_TRACE = '1'
dotnet run --project src/OpenRevelare.Gui -c Release
```

正常关闭应用后查看 `%TEMP%/openrevelare-performance-<pid>.json`；原来的 `openrevelare-render-trace.log` 保留。关闭诊断时没有分段计时及统计更新。JSON 仅包含平台、运行时、核心数、阶段耗时、计数及工作集；不记录原片名称或路径。

需要 A/B 比较时，在一次新的进程中设 `OPENREVELARE_PREVIEW_WARMUP=0`，保留相同卷、窗口、显示器与操作顺序；正常预热组删除该环境变量。此开关只用于诊断。

建议每组独立启动，记录以下场景并保留原始 JSON：

1. 首次打开同一测试卷：记录读取与首次发布，注明磁盘是否由 OS 缓存，不把刚写出的合成 TIFF 称为冷磁盘。
2. 已解码后的前后切帧：每次停留至少 500 ms 允许预热，连续 30 次；再快速连续切帧，检查取消和过期发布。
3. 拖动同一滑块 10 秒并释放，记录拖动总耗时及高分辨率收敛。
4. 在相同位置放大、平移和返回，记录区域请求。
5. 导出相同帧、格式和尺寸，记录全尺寸读取及渲染写入。

## 字段解释

`Phases` 每项包含会话总次数、保留样本数、总时长、最大值、P50 与 P95。分位数采用 nearest-rank，最多保留每阶段最近 2048 个样本；总次数／总时长／最大值覆盖整个会话。异常尝试也记录耗时。嵌套与并发阶段不能相加。

主要阶段包括 `decode.preview`、`frame.switch.decode-and-load`、`frame.switch.first-publication`、`preview.pipeline`、`preview.scene`、`preview.histogram`、`preview.fallback`、`preview.publish`、`preview.total`、`preview.warm.prepare`、`drag.total`、`export.render-and-write`。首帧发布指模型向呈现层发布完成，不代表屏幕扫描输出的时刻。`preview.pipeline/scene/histogram` 同时计入前台和后台准备；`preview.warm.prepare` 单独提供后台总量。

`Counters` 区分解码命中／在途合并／未命中、准备缓存命中／未命中、预热保存／取消／失败／过期，以及被拒绝的前台过期发布。未出现的计数项表示这次会话没有发生该事件，不代表没有执行检测。

## 回归与人工验收边界

自动测试覆盖同路径替换、删除重建、读取途中变化、平场参考变化、区域键隔离、虚拟副本共享像素、准备缓存容量／内存压力／旧代数失效、邻帧实际预热与正式参数一致性，以及缓存与重新计算的像素一致性。

真实设备 RAW 性能、低内存机器长时间运行及 macOS 真机呈现仍须按上述场景实测。自动测试与生成 TIFF 基准不冒充这些验证。
